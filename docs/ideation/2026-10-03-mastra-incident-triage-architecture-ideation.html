What the evidence says

Grounding Context

The current incident-triage project already has the right fundamental trust split: deterministic software owns evidence, validation, policy, approval staging, provenance, and evaluation; the LLM contributes one bounded judgment. The architectural weaknesses are around that core: synchronous webhook execution, terminal-only persistence, positional evidence identity, approval state not bound to an exact run artifact, incomplete version capture, mixed HTTP trust surfaces, and liveness-only health.

The Mastra workspace provides an appropriate independent deployment boundary and current Mastra APIs provide typed workflows, storage, suspend/resume, observability, authentication middleware, request context, and custom routes. None of those capabilities automatically creates a safe incident system; the application must still define the authoritative data and policy contracts.

Central conclusion

Improve the deterministic shell before making the agent more capable. The highest-value changes reduce ambiguity during delivery, recovery, evidence handling, approval, and release—not prompt sophistication or agent count.

I1

Postgres incident case engine

Durable intake and executionConfidence 93%Complexity High
Description
Turn intake into a short authenticated transaction: persist an immutable delivery envelope and initial checkpoint, return 202, then advance the case asynchronously. Separate delivery identity, incident correlation, and workflow attempt; use an append-only transition journal, fenced leases, scheduled retries, and an outbox so interrupted work resumes without duplicating the model judgment.
Basis
direct: The current handler performs evidence retrieval, inference, terminal persistence, and replay-claim release inside the request, while workflow transitions exist only in memory. Payment idempotency and durable workflow histories provide matching external precedent.
Rationale
This establishes the public reliability contract everything else depends on. Postgres is already part of the system, so it captures most durability value without introducing Kafka or Temporal before the workload justifies them.
Downsides
Requires a real state machine, worker leasing, retry policy, operational cleanup, and careful transactional boundaries. It is the largest change and should be designed before the Mastra port, not discovered during it.
I2

Content-addressed evidence ledger

Evidence and reasoning integrityConfidence 95%Complexity Medium
Description
Replace positional identifiers such as log:0 with stable identities over source locator, observation time, collector version, redaction version, and normalized payload digest. Seal each run's evidence manifest with freshness, trust-tier, checksum, and collection metadata.
Basis
direct: Current evidence records have only five fields, positional IDs shift when ordering changes, and duplicate IDs can collapse in maps without proving freshness, collector identity, or content integrity.
Rationale
Stable evidence identity becomes the shared primitive for citations, approval binding, replay, cache reuse, provenance audit, and change detection. It also lets deterministic code prove exactly what the model saw.
Downsides
Canonicalization rules must be stable and privacy-aware. Storing digests does not remove retention obligations, and raw sensitive evidence may need a separate protected store.
I3

Single-use governed resume permit

Approval and action authorityConfidence 94%Complexity Medium
Description
Use Mastra suspension as a workflow pause, but make application approval an authenticated, expiring, single-use capability over the exact checkpoint, evidence manifest, bounded judgment, catalog and policy versions, staged parameters, and verification plan. Resume re-runs deterministic safety checks before recording the simulation-only outcome.
Basis
direct: Current approval records bind primarily to incident and catalog IDs, omit actor, role, reason, checkpoint, and evidence identity, and live in a separate JSON store rather than durable workflow state.
Rationale
“Approved” becomes permission for one reviewed artifact rather than mutable ambient state. Any material change invalidates the permit and forces a new decision.
Downsides
Requires operator identity, authorization policy, expiry semantics, optimistic concurrency, and a durable audit model. For a simulation-only portfolio path, the full capability model may be staged after basic authenticated approval.
I4

Decision certification pipeline

Evaluation and replayConfidence 91%Complexity High
Description
Persist a reproducible decision capsule for every judgment: normalized incident, sealed evidence manifest, model/provider settings, prompt and schema hashes, policy/catalog/redaction versions, application build, redacted request/response, structured decision, and gate outcomes. Replay candidate inference bundles over retained capsules with all action paths disabled; prioritize material disagreements and promote repeated reviewed failures into the existing taxonomy and regression suite.
Basis
direct: The project already has strong failure discovery and executable regressions, but retained runs omit key decision-producing versions and cannot be re-executed as historical worlds. external: Datadog's incident-agent evaluation work uses reconstructed historical snapshots with real noise and feedback-derived labels.
Rationale
Operational history becomes a compounding private benchmark and release-control mechanism. Framework, prompt, policy, or model changes become attributable comparisons rather than guesses.
Downsides
Exact output reproduction is not guaranteed when hosted models change. Capsules need redaction, retention, and access policy, and replay cohorts must remain representative rather than merely large.
I5

Mastra security kernel and capability-aware readiness

Service, deployment, and security boundariesConfidence 92%Complexity Medium
Description
Keep one independently deployable image, but expose only incident-specific contracts. Give signed intake, private workflow workers, operator reads, and approval import distinct principals and policies; keep generic Mastra agent endpoints internal. Separate immutable governance events from short-lived redacted model traces, and publish reason-coded readiness that distinguishes required dependencies from explicitly degraded evidence sources.
Basis
direct: The legacy server mixes webhook, console, review, and approval mutation; approval authorization is weaker than run-review authorization. The Mastra workspace preserves a strong app/image boundary but explicitly defers application authentication and dependency-aware readiness.
Rationale
This closes the current authorization asymmetry and makes failure behavior reviewable without fragmenting the app into unnecessary services.
Downsides
One image with multiple runtime roles still needs careful process configuration and least-privilege credentials. Readiness matrices can become misleading unless backed by dependency probes and tested degraded modes.
I6

Deterministic discriminator lanes

Evidence and reasoning integrityConfidence 82%Complexity Medium
Description
Replace the fixed “collect everything” pass with policy-authored, bounded query recipes that gather supporting, disconfirming, and missing signals for plausible incident classes. Invoke the model only when class-specific evidence obligations are satisfied and require it to cite the strongest contrary evidence as well as its selected class.
Basis
external: Datadog reported that hypothesis-specific evidence gathering outperformed collecting everything and summarizing. direct: The current implementation follows a fixed exhaustive retrieval order and admits structurally valid decisions with incomplete semantic evidence.
Rationale
This can reduce latency, tokens, and irrelevant context while improving diagnostic discipline without granting the model tools or additional reasoning turns.
Downsides
The recipes can encode blind spots or become expensive policy code. This idea should remain behind an evaluation gate until retained-world tests prove it beats the simpler evidence pass.
